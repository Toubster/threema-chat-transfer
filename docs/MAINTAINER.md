# Maintainer handbook

For the maintainer and future co-maintainers. Contributors start with [CONTRIBUTING.md](../CONTRIBUTING.md); module
owners with [devtools/OWNERSHIP.md](../devtools/OWNERSHIP.md).

## 0. Hard rules

1. **Devices are touched only by the maintainer, by hand, after an explicit go.** No test, CI job, script in this
   repository or contributor ever talks to a real iPhone. CI has no self-hosted runner.
2. **Never run a canary or a test restore on an iPhone that belongs to someone else**, and never on a device of a
   user for support.
3. **No real data in the repository.** Records contain counts only; screenshots come from the demo mode or are reviewed
   device photos from test accounts. Run `make scrub` before every commit (the hooks do it).
4. **No overrides.** Do not add a switch that skips a guard, not even "for maintainers". Diagnostic tooling that needs
   one lives in the private maintainer repository and never ships.
5. **Nothing is published without the maintainer's explicit go**: no push of a new remote, no release, no tag push.

## 1. Local setup

```
git config core.hooksPath scripts/hooks      # pre-commit (staged), commit-msg, pre-push (layer 2 required)
git config user.name <handle>; git config user.email <handle>@users.noreply.github.com   # no-reply identity only
export TZ=UTC                                # in the shell for this repo: commit dates +0000 (pre-push checks both)
python3 -m venv .venv && .venv/bin/pip install pytest jsonschema
make validate strings test scrub
python3 docs/tools/check_docs.py             # guide structure, links, screenshot names
```

### Scrub layer 2 (deny list)

The deny list of real values (names, IDs, device identifiers, hosts, real counts) never enters this repository. It is
generated by `devtools/make_denylist.py` in the **private** maintainer repository into `~/.config/tm-scrub/`
(`deny.hmac`, `key`, mode `0600`). `scripts/scrub_check.py` picks it up automatically; the pre-push hook refuses to push
without it.

For CI, two repository secrets enable layer 2 on pushes to this repository (never on fork pull requests):

| Secret | Content |
|---|---|
| `SCRUB_DENY_B64` | `base64 < ~/.config/tm-scrub/deny.hmac` |
| `SCRUB_KEY` | the hex key from `~/.config/tm-scrub/key` |

Regenerate the deny list whenever private data changes (new device, new real counts) and update both secrets.

## 2. CI at a glance

| Workflow | Trigger | What it guards |
|---|---|---|
| `ci.yml` | push, pull request | `scrub`, `lint`, `core-tests`, `contract`, `importer`, `e2e-fixture`, `app` (unit + UI with MockEngine, DE + EN), `package-smoke` |
| `release.yml` | manual (`workflow_dispatch` with a tag) | builds and attests a **draft** release; never publishes |
| `upstream-watch.yml` | weekly + manual | new Threema iOS tags, new iOS builds, new Threema Android releases → issues |
| `demo-screenshots.yml` | manual | demo-mode screenshots DE + EN → pull request |

Jobs whose component does not exist yet (Swift package, Xcode project, packaging scripts, end-to-end tests) report
"not present yet" and succeed, so the skeleton stays green while the owners land their parts. Set the repository
variable **`CI_STRICT=1`** once all components exist (at the latest for 0.5.0): from then on a missing component fails
the job. `release.yml` is always strict.

Pinned tools: Actions by commit SHA (update with `git ls-remote --tags https://github.com/<action>` and keep the version
comment and the `scrub:ok sha1` marker on the line), Python dev tools in `.github/ci-requirements.txt`, Xcode via
`XCODE_APP` in the workflow files.

## 3. Per-build canary procedure

Goal: decide whether a new iOS build may become `verified` in `compat/ios.json`. Policy:
[COMPAT-POLICY.md](COMPAT-POLICY.md). Background: [RESTORE-MECHANISM.md](RESTORE-MECHANISM.md).

### 3.1 Test device

A dedicated test iPhone on the target build (interim rule D6: until a spare device exists, the maintainer's own device,
and only the acceptance run of COMPAT-POLICY.md §1.1). State for 24A437: no-op canary 2026-10-01 and an app run
2026-10-03 that stopped at the device's own refusal (Find My was on, `MBError 211`, nothing changed) are recorded in
`compat/records/ios/24A437.json`; the acceptance run with a restore executed by the app is still open
(`comment_code: acceptance_partial`). Turn Find My off **before** that run and record it as a second `app_run` (or
`C3`), structural counts only. Before every run:

- test Apple Account, test Threema ID (test licence), test Android device; never personal accounts on the test device;
- Find My off, automatic updates off, an archived Finder backup **and** an iCloud backup from the same day;
- seeds that the gate must keep intact: a wallpaper, three Shortcuts, changed notification settings, granted app
  permissions, five photos stored on the device, an SMS with an attachment, a calendar account, keyboard learning data,
  an offline download, a keychain item with `WhenPasscodeSetThisDeviceOnly` (test app via free provisioning),
  optionally a test Apple Watch;
- a synthetic Android backup for the test Threema ID, generated **outside** the repository with
  `fixtures/gen_android_backup.py` (the real test ID must never be committed).

### 3.2 Runs

| Run | Content | Expected | When |
|---|---|---|---|
| C0 | backup → reboot → backup → gate | green; this is the churn baseline of the build | every build |
| C3 ×2 | full wizard run with the release-candidate DMG and the fixture import | `ok` / `ok_with_notes`, no waiver, no manual analysis, Threema shows the history, seeds intact | every build and every release |
| R1 | `rollback-threema` after a deliberately broken store | `ok` after the rollback | every minor version |
| C1a | trimmed payload through the private tool chain | gate **red** (the detector still works) | every major iOS version |
| R3 | Apple-native restore from iCloud **and** from the archived Finder backup | guide S22 matches the device; state as before | every major iOS version |
| Negative | Find My on, cable pulled while sending, Mac sleep, airplane mode off, wrong iPhone, photo taken in the window | the expected code each time; nothing changed | once before 1.0 |
| Large | local photo library ≥ 30 GB | space, duration and deadline fit; decides the 20 GB limit | once before 1.0 |
| Offline setup | Setup Assistant in airplane mode | S16 texts and the "Later" path confirmed | next run |
| Language | iPhone in German and in English | all † menu paths checked, device photos taken | before 0.9.0 |

Exact commands for the non-wizard runs (C0, C1a, R1 trigger) are in `devtools/device-run.md` (maintainer only).
Never start a C3 when C0 of the same build is red.

### 3.3 After a run

1. Keep the session folder of the run on the maintainer Mac only. Nothing from it is copied into this repository.
2. `python3 devtools/make_compat_record.py <session folder> > compat/records/ios/<build>.json` writes counts, verdicts,
   gate classes and observed note classes; no identifiers.
3. Read the record line by line. Then `python3 scripts/scrub_check.py --require-layer2 --paths compat/records/ios/<build>.json`.
4. Interpret: C0 and both C3 green → the build can be `verified`. Any red verdict → it stays `unknown` (or becomes
   `blocked` if an earlier `verified` entry turns out wrong), and an issue documents the gate classes.

## 4. Adding or changing a compat entry

### 4.1 iOS build

1. Evidence per §3 (record committed under `compat/records/ios/<build>.json`).
2. In `compat/ios.json` set `status: "verified"`, `verified_on` (date), `evidence: "records/ios/<build>.json"`,
   `expected_notes` = exactly the note classes observed in the C3 runs (never more), `min_app` = the release that ships
   the entry. Remove `comment_code`.
3. `make validate` (schema + catalog) and `make test`.
4. CHANGELOG (DE + EN): "iOS <version> (<build>) supported". Version bump: a new compat entry changes behaviour for users
   of that build → patch release `X.Y.(Z+1)`; one number for app, core and importer; row in `VERSIONS.md`.
5. Release per §6.

**Blocking a build** (problem found after release): set `status: "blocked"` with a `comment_code`, release immediately.
Old app versions keep their list; the 90-day hint and the release notes point users to the update.

### 4.2 Threema iOS model

1. `upstream-watch` opens "Threema iOS <tag>: model changed" (or "unchanged"; then nothing to do unless a version must be
   blocked).
2. `model/build-momd.sh` with the new tag: compile, compute `version_hashes_sha256`.
3. Review the model diff and the importer mapping (`importer/`), add tests for every changed entity, run the importer
   check suite and the fixture end-to-end tests.
4. Simulator gallery (§5) with the imported fixture store on the new Threema build.
5. One C3 run on the test device with the new Threema version.
6. Add the model to `compat/threema-ios.json` (keep the old one; the bundle carries both), add the `.momd` and its
   digests (allowlist block, private assembly script), release.

### 4.3 Android backup format

1. `upstream-watch` reports a higher backup version constant in Threema for Android.
2. Read the format change in the Threema for Android source (implement from the source, copy no code), extend
   `core/tmcore/lib/android_normalize.py` and the fixture generator, add tests.
3. Verify with a synthetic fixture **and** a real test backup from the test Android device (outside the repository).
4. Add the format to `compat/android.json` (`verified_formats`, `max_known_format`), release.

## 5. Simulator harness (`devtools/sim-harness/`)

Maintainer-only, needs full Xcode and a Threema iOS build from source:

The scripts keep everything in one workspace folder, `$TCT_SIM_ROOT` (default `~/.cache/threema-chat-transfer-sim`):
`ref/threema-ios` (checkout), `build/` (DerivedData, packages) and `sim/` (app snapshot, inject library, throwaway
identity, runs).


- `build-threema-sim.sh`, `prepare-sim-app.sh`: build the Threema app for the Simulator at the pinned commit.
- `ThreemaSimInject.m` + `build-inject.sh`: an injected library that keeps a **network kill-switch on**, injects a
  throwaway identity (`gen_test_identity.py`) and opens chats in-process; `swap_own_identity.py` rewrites the store to
  that identity.
- `sim-gallery.sh`: screenshots of the chat list and selected chats of a store; `sim-verify.sh`, `store_diff.py`,
  `summarize_diff.py`: what the app wrote to the store.
- `dump_model.swift`, `make_sample_db.swift`: inspect and seed Core Data models.

Use it for every new Threema model and every importer change, with **fixture stores only** in anything that leaves the
maintainer Mac. The Simulator cannot test restores (no `lockdownd`, no `BackupAgent2`, no Setup Assistant); it only
shows that Threema opens and renders an imported store without unexpected writes. It is never part of the shipped
product or of CI.

## 6. Release

1. Version: same `X.Y.Z` for app, `tmcore`, importer; `CFBundleVersion` increases; row in `VERSIONS.md` with commit
   hashes; CHANGELOG section in German and English.
2. Signed tag `vX.Y.Z` (local). After the go to push: run **release** (`workflow_dispatch`, input `tag`). It checks the
   version files, builds, signs ad-hoc, verifies the bundle, builds the DMG, `SHA256SUMS`, SBOM, source bundle,
   attests and creates a **draft**.
3. Download the draft on clean macOS VM users (14, 15, 26, 27): Gatekeeper flow ("Open Anyway"), `selftest`, demo run.
   Take the Gatekeeper screenshots if they changed (§7).
4. C3 with exactly this DMG on the current iOS build (§3); record up to date.
5. `minisign -Sm SHA256SUMS` locally (key offline, never in GitHub); upload `SHA256SUMS.minisig` to the draft.
6. `packaging/verify-bundle.sh --dmg <dmg>` passes, including the image privacy checks: no extended attribute on any
   item (`com.apple.provenance` would link releases to the build Mac; build from Terminal or CI, never from inside a
   downloaded third-party app), HFS+ dates in UTC, neutral PDF metadata, no build-machine names, the account name
   only inside repository links. Then scrub layer 2 over the DMG content and the release notes:
   `hdiutil attach -readonly -nobrowse <dmg>` → `scripts/scrub_check.py --layer 2 --require-layer2 --paths <mount>`;
   `scripts/scrub_check.py --require-layer2 --text-stdin release-notes < notes.md`.
7. **Publish by hand**, only after the maintainer's explicit go.

"Is damaged" in any own test is a release blocker. There is no auto-updater in version 1.

## 7. Screenshots and device photos

- **Names** come from `docs/images/screenshots.json` (single source for the guide, the demo autopilot and the workflow).
  `python3 docs/tools/check_docs.py` checks that both guides reference every app screenshot and no unknown name.
- **App screenshots**: only from the demo mode (`demo-screenshots.yml`, or locally `make demo-screenshots INSTALL=1`:
  the signed app with the real engine on the virtual iPhone, driven by its demo autopilot); they carry the PNG text
  marker `tm-demo=1` and a visible "DEMO" watermark. Look at every picture before committing.
- **Gatekeeper and device photos**: test accounts only, no names, no notifications, clean status bar, EXIF removed.
  Mark them with `python3 .github/scripts/mark_png.py --marker tm-reviewed=1 <files>` (also strips all other metadata)
  only **after** looking at every picture, and put them in a pull request for review.

## 8. Upstream watch triage

| Issue | Action |
|---|---|
| New iOS build | read the linked `BackupAgent2` / `MobileBackup` diff; plan C0 + 2× C3 (§3); betas from June on |
| Threema iOS model changed | §4.2 |
| Threema iOS model unchanged | nothing to do (newer app versions with the same model hash are allowed); close |
| Threema Android backup version raised | §4.3 |

## 9. Beta

Pre-releases (0.9.x) go privately to five to ten testers with their **own spare devices** or a freshly set-up iPhone.
Feedback only via diagnostic reports. Exit criteria: at least eight successful runs on at least two iOS builds, zero
data loss, every red run explained, the most frequent drop-out point known (Gatekeeper?).

## 10. Dependencies

- python-build-standalone: yearly or for security fixes; new URL + sha256 in `packaging/python.lock`.
- Wheels: hashes in `core/requirements.lock`; `pip-audit` before each release.
- pymobiledevice3: only together with a C0 + C3 device run.
- Actions: §2.

## 11. Exit criterion

When Threema officially supports moving from Android to iOS, the app only points to the official way. Thanks to the
built-in allow-list, an abandoned version never touches a new iOS build.
